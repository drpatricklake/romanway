# Registration, classroom expansion and support — pilot handoff

This branch prepares role-first registration at `/register.html` and isolated classrooms. It does not turn on public registration or activate payment links. Existing Google accounts and the pilot classroom retain their current paths. Do not invite children into the new flow until the launch prerequisites below are complete.

## What is implemented

- Student path: six-digit class code + pseudonymous username + password. No student name or email field. Internal Auth address is an HMAC of class ID and normalized username at `students.romanway.invalid`; no email is sent there. This is pseudonymization, not anonymous or zero-personal-data processing.
- Teacher/parent: Google or verified email/password; School, College or Homeschool; adult attestation; Patrick approves each pilot teacher by UID before class creation. One teacher may create two classes. Class count and invitation reservation use transactions. Six digits are convenient, not a security boundary: App Check and rate limits gate public student lookup/creation; teacher approval gates shared work.
- Independent: verified Google/email; explicit 13+ attestation. Adult confirmation is separate. Learners aged 13–17 never receive support links. Learners can request class membership later. The pilot supports one active class per learner; no silent transfer of private tutoring history.
- Class selection, six-digit code display, managed-student roster, teacher-owned password reset with token revocation and audit record. Passwords never enter Firestore. New passwords are displayed once to the teacher and can be changed by the learner. They are not automatically expiring or single-use.
- The existing course's instructor dashboard, roster, assignments, Circus, Atrium and Arena use the selected class root. Teacher permissions depend on Firestore staff records, not a UI role. Personal progress remains in the existing users/chunks schema, avoiding a bulk migration. Active class membership authorizes a teacher to see the learner's overall saved course work, not only new work after joining; tell learners before joining.
- Patreon/Ko-fi URLs are server configuration, HTTPS host-restricted, returned only for adult teacher/independent accounts, and rendered only on their account dashboard. No payment, paid XP, tier webhook or supporter-credit automation is active. No URLs have been supplied.

## Launch prerequisites (registration stays off until completed)

1. Deploy and verify the reviewed Firestore rules first. Password accounts are accepted only after server-managed account provisioning and email verification. Client writes to account-role, invitation lookup, rate-limit, audit and class-count documents are denied.
2. Enable Firebase Email/Password. Keep Google enabled. Authorize production and preview domains as appropriate. Configure Firebase App Check reCAPTCHA Enterprise for student lookup/creation. API refuses student operations without a verified App Check token; use emulator/mocked tests, not an enabled debug token in production.
3. Provision a dedicated server identity with only required Auth administration and Firestore data access, restricted to this Firebase project. Vercel currently has **no configured environment variables**. Preferred long-term: workload identity federation; the existing GitHub rules-deployment identity is not automatically a Vercel runtime identity. The implementation accepts Application Default Credentials or `FIREBASE_ADMIN_CREDENTIALS` (server-only service-account JSON). Do not put credentials in GitHub, browser code, NEXT_PUBLIC variables, or messages. No credentials are generated by this change.
4. Set server-only `ROMANWAY_USERNAME_SECRET` to a strong random secret (at least 32 random bytes); preserve it durably. Changing it changes student login addresses and requires a migration. Set `ROMANWAY_APPCHECK_SITE_KEY` to the public reCAPTCHA Enterprise site key. Only after staging verification set `ROMANWAY_REGISTRATION_ENABLED=true`.
5. Optional `ROMANWAY_PATREON_URL` and `ROMANWAY_KOFI_URL`. They remain absent until real URLs are provided. Institutional payment entitlements must be server-owned; Stripe/PO billing is a later integration, not part of this pilot registration.
6. Publish a privacy notice and direct school/parent notice covering identifiers, saved answers, scans, free-text messages, processors, retention, access/deletion and permitted educational use. Establish a deletion/export response process, school agreements and appropriate school authorization or verifiable parental consent. A checkbox is an attestation, not a complete consent mechanism. Do not market the app as COPPA-certified/compliant solely because this flow avoids names/emails. Have the school/district privacy reviewer or qualified counsel review the under-13 rollout.
7. Rate-limit documents contain a keyed hash of IP/time bucket, not raw IP, and have `expiresAt`. Configure TTL deletion or a scheduled cleanup (TTL can incur charges). Add operational error monitoring without logging request bodies, passwords, tokens, student messages or reset responses. Provider infrastructure may process IPs independently.
8. Before broad signup, exercise the real Auth flow, App Check, revocation, class switching, saved work, password resets, teacher denial and cross-school isolation in a staging Firebase project. Automated service mocks and Firestore rules tests do not replace that live acceptance test. Test school network accessibility and actual iPhones too.

## Architecture and costs

Serverless reduces server administration; it does not eliminate quotas, billing, security, backups, retention or incident management. Vercel does not impose a blanket 50-student limit. Firebase Auth's MAU allowances are different from a hosting user cap. Do not promise that 30,000 users stay free.

Keep shared curriculum and art as versioned cacheable static assets, not per-user Firestore records. Animate on the device; save only equipment selection, unlocks and final activity results. No Firestore writes for animation frames. On-demand loading and a static/reduced-motion fallback are the recommended next animation pilot. Storage size, download traffic and device memory are three separate budgets.

Illustrations, not measured forecasts:
- 100 shared assets × 1 MB = about 100 MB stored once.
- 30,000 first-time users downloading 10 MB each = about 300 GB delivered, before later uncached updates. Browser/CDN caching can reduce repeat traffic, not eliminate first downloads.
- 10,000 daily active learners × 100 document reads = 1 million reads/day; × 20 writes = 200,000 writes/day. Both exceed Firestore's free daily quotas (50,000 reads / 20,000 writes). Monthly registered users are not the same as daily active users.
- The current chunked whole-state save format is compatibility code; as data grows, measure changed chunks, write rates and listener reads before replacing it with per-activity documents. Do not blindly rewrite every answer to a growing single enrollment document.

Set billing alerts at several levels, per-user write/query limits, indexed bounded queries, and separate alerts for bandwidth, Auth, database and uploads. Budget alerts do not cap spending. Review usage at 100, 1,000 and 10,000 active learners and price institutional support from observed costs and support workload. Vercel Hobby is for personal noncommercial use; review Pro/commercial terms before monetization. Check Cloud Storage bucket region/plan pricing before enabling scans or hosting large media there.

## Follow-on work

Full institutional administration, Stripe webhooks/invoice reconciliation, paid entitlements, formal school contracts, automatic export/deletion workflows, closed-class code rotation/transfer UI and publication of named supporter credits are not shipped by this PR. The `tier` field is server-created as `free`; no client can claim paid status. Keep core course access independent of donations. Do not paywall essential student feedback or accessibility.
